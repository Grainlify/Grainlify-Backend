## Part 1: fields decoded from GitHub and thrown away

Two fields have now been found decoded at the JSON boundary and never
persisted. The first, `fork`, cost a farmable public leaderboard: nothing
downstream could filter forks *even in principle*, because the value never
reached the database. The second, `owner.type`, was found while asking a
different question.

Both live in the same struct. This is the full list, so the third one is found
deliberately rather than by accident.

Persisted columns on `projects`: `id, owner_user_id, github_full_name, status,
webhook_id, created_at, updated_at, github_repo_id, verified_at,
verification_error, webhook_url, webhook_created_at, ecosystem_id, language,
tags, category, github_app_installation_id, deleted_at, stars_count,
forks_count, needs_metadata, description, is_fork, fork_checked_at`

`split_part(github_full_name, '/', 1)` as the thing being replaced. Do not
add columns one at a time as each is missed.

## Part 3: decisions waiting on a person

These are grouped deliberately. Both are cases where **the system is more
permissive than the marketing describes**, and they should be decided together
rather than patched when someone notices.

### 3.1 Per-repo selection

There is no per-repo selection in the product. `syncInstallationRepositories`
lists every repo the installation can see and creates **and auto-verifies** a
project for each, filtering only on `private`. `POST /projects` accepts a
single repo and has created **zero** of the projects in production.

GitHub's "All repositories" is the default **and covers future repos**, so it
is a standing subscription rather than a one-time import: every repo those
accounts create from now on becomes a verified Grainlify project
automatically. The fork count is a running total, not a backlog.

The likely answer is "stop indexing what nobody selected", not "add another
filter".

### 3.2 Should `FoundingSlots` enforce anything?

It does not enforce. `WaveFor(sequence)` uses the slot numbers only to choose a
multiplier band:

```
sequence <= FoundingSlots                  -> founding, x1.5
sequence <= FoundingSlots + WaveTwoSlots   -> wave two, x1.25
otherwise                                  -> open,     x1.0
```

Nothing refuses. Member 101 is not rejected; they get the wave-two multiplier.
**100 is a boundary between tiers, not a capacity** — as a cap it exists only
in test assertions. Tiers are 100 / 400 / unlimited.

Consequence for copy: any surface implying scarcity ("spots", "slots left", a
count against a capacity) describes behaviour the code does not have. A
scarcity audit of UI, email and notification copy is queued — list where,
do not rewrite yet.

### 3.3 Two share-holders without KYC

31 members hold founding shares; 29 are KYC-verified, **2 are not**. A share
held by an unverified person needs an answer at claim time. Nothing to build
now; it is a policy question against the payout path.

### 3.4 Founding share counting

42 share rows across 31 members: 24 hold one row, 3 hold two, 4 hold three.

## Part 4: how to know something is actually shipped

`npm run verify-deployed` (frontend repo) checks three mechanical conditions:
clean working tree, local HEAD equals `origin/main`, and **the deployed
artifact reports that same commit** — via the `grainlify:commit` meta tag and
the API's `/version`.

It exists because three "verified" claims in one session were false: work
reported as shipped that was never committed, work merged but not deployed,
and 665 passing tests run against a tree that never left the machine. No test
catches those; the gap is between the tree and production.

It exits non-zero when it **cannot** check as well as when a check fails.
Run it before reporting anything as shipped.

See also `docs/VERIFICATION-TRAPS.md` for the checks that reported success
while proving nothing, including the shell flags that silently return empty
and the structural guard that matched one gate of three.

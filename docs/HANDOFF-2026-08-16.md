## The one thing worth carrying forward

Every recurring failure in this session is the same shape: **two lists that
have to agree, with nothing comparing them.**

| The two lists | What diverged | Cost |
| --- | --- | --- |
| What the GitHub struct decodes vs. what the INSERT persists | `fork`, `owner.type`, `description`, `repository_selection` | a farmable public leaderboard; 106 projects invisible; a maintainer's choice overridden |
| A shared component vs. a local copy of it | rail button, rank badge, issue overlay | wrong-looking icon, a stretched badge, two URLs for one screen |
| A filter applied in one query vs. the others reading the same table | fork exclusion on ranking but not Browse, recommendations, ecosystem or admin counts | forks on the first page a contributor sees |
| Notification link literals vs. the routes the app serves | `/settings?tab=` and `/settings?subtab=` | blank page, recoverable only by browser back |

Four instances, four surfaces, one failure mode. In every case:

- **nothing enforced the agreement** - no test, no type, no review step compared
  the two lists
- **it surfaced weeks later as a visible bug**, never at the moment it was
  introduced
- **the fix was to make the second list unnecessary**, not to correct it:
  extract the component, export the predicate, build the link, persist the
  field

The reusable move is to notice when a change creates a second list, and either
collapse it or write the check that compares them. A guard that reads one list
and asserts against the other is cheap; discovering the divergence from a
user's bug report is not.

The guards that now exist for this: `TestSyncInsertPersistsTheFieldsItDecodes`,
`TestEveryProjectSurfaceExcludesForks`, `TestEligibilityPredicateAppliesEverywhere`,
`TestNoNotificationCallSiteWritesAnUnroutablePath`. Each one reads a list and
asserts against another list, and each was written after the corresponding bug
reached production.

## Part 1: fields decoded from GitHub and thrown away

### First, the headline: owner grouping has no stable identifier

Every owner-grouping query resolves an owner by
`split_part(github_full_name, '/', 1)` - a **string parse of a mutable value**.
GitHub logins can be renamed, and a rename silently splits one owner into two
groups. Nothing errors. Nothing reconciles. The count goes up by one and looks
like growth.

**The 30-owner figure in section 2.2 was produced by that parse.** If a rename
has already happened in the indexed set, it may be wrong today - and it is
about to be quoted externally.

The same parse appears on the repo side too: the `.github` exclusion is
`split_part(p.github_full_name, '/', 2) != '.github'`, which reads the repo
NAME out of the same mutable string. It is used in Browse/List and in
recommendations. A repo rename breaks it exactly as an owner rename breaks the
owner grouping, and with `github_repo_id` already stored there is a stable key
available for the repo half today.

So persisting `owner_id`, `owner_login` and `owner_type` is not three
nice-to-have columns. It is **replacing a string parse with a key**. `owner_id`
is the one that matters: it survives renames, and it is what any owner count,
owner page or owner grouping should join on. The field list below is the
supporting detail, not the point.

**THREE** fields have now been found decoded at the JSON boundary and never
persisted:

1. `fork` - cost a farmable public leaderboard. Nothing downstream could filter
   forks *even in principle*, because the value never reached the database.
2. `owner.type` - found while asking a different question.
3. `description` - found third. The sync's INSERT lists eight columns and
   `description` is not among them, although `InstallationRepository.Description`
   is decoded. Result: **0 of 106** projects awaiting metadata have a
   description, and every one of them is invisible to the catalogue until a
   human types one in.

### This is a review gap, not three coincidences

The sync's INSERT column list has never been checked against what the struct
decodes. Nothing compares them, so a field can be parsed and silently dropped,
and the only way any of these three was found was by investigating a symptom
weeks later.

**A test would have caught all three.** Assert that every field
`InstallationRepository` decodes is either written by the sync or named in an
explicit "intentionally dropped" list, with a reason. `Permissions` belongs in
that list - persisting a stale permission is worse than not having it. `Name`
belongs in it - derivable from `FullName`. `Fork`, `Owner.Type` and
`Description` would all have failed it on the day they were added.

Same shape as the fork-exclusion guard in `internal/ranking`: the mistake was
never "a condition was written wrongly", it was "nobody compared two lists that
have to agree".

Both live in the same struct. This is the full list, so the third one is found
deliberately rather than by accident.

Persisted columns on `projects`: `id, owner_user_id, github_full_name, status,
webhook_id, created_at, updated_at, github_repo_id, verified_at,
verification_error, webhook_url, webhook_created_at, ecosystem_id, language,
tags, category, github_app_installation_id, deleted_at, stars_count,
forks_count, needs_metadata, description, is_fork, fork_checked_at`

| Field | Persisted? | Would a decision want it? |
| --- | --- | --- |
| `ID`, `FullName`, `Description` | yes | — |
| `Fork`, `StargazersCount`, `ForksCount` | yes | — |
| `Owner.ID` / `Owner.Login` | **no** | **Yes** — as above. |

### 2.3b What approving a social-follow submission awards — ANSWERED

Traced read-only, because a public campaign depends on it.

**Approval awards nothing.** It sets `status = 'approved'` and sends a
notification. No wave, no sequence number, no share row, no multiplier. The
handler's own comment is explicit: following is "an eligibility requirement for
the Founding Contributor Pool, worth zero shares", and the notification says
"You're eligible for", not "you are". `founding.Eligible` re-reads that status
at settlement, so approval is a gate, not a grant.

**Founding status comes from identity verification.** `AssignWave` has exactly
one caller — `founding.OnVerified` — reached from
`internal/handlers/founding.go:32` when KYC verification succeeds. That is where
a sequence number is issued and a multiplier band assigned.

Consequences for campaign copy promising founding status to 300 approvals:

1. **Approvals do not assign waves at all.** An approved contributor who never
   completes KYC has no sequence number and no multiplier.
2. **The order deciding the multiplier is KYC completion order**, not approval
   order. Approval #12 can land in a later band than approval #200.
3. **The founding band is 100, not 300** — and it is a multiplier boundary, not
   a capacity (see 3.2). Nobody is refused; past 100 gives x1.25, past 500
   gives x1.0.

**Nothing caps approvals.** No limit, count check or capacity test exists on the
approval path.

The promise is wrong in two independent ways at once: approvals are not what
grants founding status, and 300 is not a boundary that exists anywhere.

## Part 2b: one definition, several copies — this is a class now

Three instances found, all the same shape: a thing with no single owner gets
reproduced by hand and the copies diverge.

| Copy | How it diverged | Fixed in |
| --- | --- | --- |
| Sidebar rail button | Every rail item was a branch of one `.map()`, so adding the support item meant reproducing the styling. It drifted on icon size, idle surface, inset bevel, hover and active state. | `RailButton`, #1003/#1005 |
| Org rank badge | A verbatim port of `ProfilePage`'s badge markup, which the flex row then stretched into a tall rectangle. | shared `RankBadgeCard`, #1004 |
| Issue detail overlay | `DiscoverPage` rendered its own, behind its own `?dIssue=` parameters, parallel to Dashboard's `?issue=`. The same issue opened from two places was two screens with two URLs. | lifted to Dashboard, #1008 |

None was caught by review. Each surfaced as a visible bug weeks later, and in
each case the fix was not "correct the copy" but "make a second copy
unnecessary".

**What to look for:** a component rendered by exactly one caller with styling
or state defined inline is a copy waiting to happen. The moment a second caller
needs it, somebody reproduces it rather than extracting it, because extracting
is the larger diff.

**This is one instance of the pattern at the top of this document** — the same
two-lists failure, at the component layer rather than the data layer.

## Part 3: decisions waiting on a person

These are grouped deliberately. Both are cases where **the system is more
permissive than the marketing describes**, and they should be decided together
rather than patched when someone notices.

### 3.1 Per-repo selection

There is no per-repo selection in the product. `syncInstallationRepositories`
lists every repo the installation can see and creates **and auto-verifies** a
project for each, filtering only on `private`. `POST /projects` accepts a
single repo and has created **zero** of the projects in production.

GitHub's "All repositories" is the default **and covers future repos**, so it
is a standing subscription rather than a one-time import: every repo those
accounts create from now on becomes a verified Grainlify project
automatically. The fork count is a running total, not a backlog.

The likely answer is "stop indexing what nobody selected", not "add another
filter".

### 3.2 Should `FoundingSlots` enforce anything?

It does not enforce. `WaveFor(sequence)` uses the slot numbers only to choose a
multiplier band:

```
sequence <= FoundingSlots                  -> founding, x1.5
sequence <= FoundingSlots + WaveTwoSlots   -> wave two, x1.25
otherwise                                  -> open,     x1.0
```

Nothing refuses. Member 101 is not rejected; they get the wave-two multiplier.
**100 is a boundary between tiers, not a capacity** — as a cap it exists only
in test assertions. Tiers are 100 / 400 / unlimited.

Consequence for copy: any surface implying scarcity ("spots", "slots left", a
count against a capacity) describes behaviour the code does not have. A
scarcity audit of UI, email and notification copy is queued — list where,
do not rewrite yet.

### 3.3 Two share-holders without KYC

31 members hold founding shares; 29 are KYC-verified, **2 are not**. A share
held by an unverified person needs an answer at claim time. Nothing to build
now; it is a policy question against the payout path.

### 3.4 Founding share counting

42 share rows across 31 members: 24 hold one row, 3 hold two, 4 hold three.
So 7 people account for all 11 extra rows. **42 was never a defensible reading
of "claimed"** — it counts grants, not people. The people-count is 31.

## Part 4: how to know something is actually shipped

`npm run verify-deployed` (frontend repo) checks three mechanical conditions:
clean working tree, local HEAD equals `origin/main`, and **the deployed
artifact reports that same commit** — via the `grainlify:commit` meta tag and
the API's `/version`.

It exists because three "verified" claims in one session were false: work
reported as shipped that was never committed, work merged but not deployed,
and 665 passing tests run against a tree that never left the machine. No test
catches those; the gap is between the tree and production.

It exits non-zero when it **cannot** check as well as when a check fails.
Run it before reporting anything as shipped.

See also `docs/VERIFICATION-TRAPS.md` for the checks that reported success
while proving nothing, including the shell flags that silently return empty
and the structural guard that matched one gate of three.
